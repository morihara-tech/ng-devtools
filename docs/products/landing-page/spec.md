# トップページのランディングページ化・ダッシュボード分離 仕様書

## 問題定義
- **対象ユーザー**: 検索エンジン経由でdevToolsに初めて訪れる開発者（JSON整形・UUID生成等を検索する層）
- **課題**: 現トップページ（/ja, /en）はカードグリッド形式のダッシュボードUIで、数ヶ月間Google Search Consoleで「クロール済み-インデックス未登録」が継続している。技術的欠陥（SSG出力へのコンテンツ欠落、canonical/hreflang不整合、cookie同意バナーの侵入型インターステイシャル、font最適化未適用等）はすべて特定・修正済みで、修正後に本番で再クロールされたことも確認済みだが、なお解消しない。ja版トップページは既にインデックス登録されているが、en版トップページのみ拒否が続いている（個別ツールページ・記事ページはen版も多数インデックスされており、ロケール単位の一律拒否ではない）。技術的要因を使い尽くした結果、「カードグリッドという構造自体がテンプレート的で、他ページとの差別化・独自価値に乏しいとGoogleに判断されている」という仮説に至った。
- **ゴール**: 検索エンジンから独自価値のあるコンテンツとして評価される静的ランディングページを新設し、既存の操作型ダッシュボード（カードのドラッグ&ドロップ・リサイズ・localStorage永続化）は`/dashboard`へ分離してnoindex化する。
- **成功指標**: 新ランディングページ（/ja, /en）がGoogle Search Consoleで「インデックス登録済み」になること。少なくとも次回GSC再クロール後に「クロール済み-インデックス未登録」が解消していること。

## この仕様にした理由
- 競合サイト調査（W3Schools Tools、DevBuddy、DevToolCore、Regex101/RegexOne、DevFormatters、Vercel/Supabase等）の結果、「記事コンテンツのみを主役にする」設計は2026年時点で効果が薄いことが判明した（記事単体では上位表示されず、RegexOne型の「学習コンテンツとツールの統合」が有効という知見）。当初案（記事を前面に出す）を修正し、**記事をツールの信頼性の証明として統合配置する方式**を採用した。
- 競合が強い2軸（プライバシー訴求・機能網羅性）は個人運営・12ツールのこのサイトでは正面から勝ちにくいため、「実装を検証した独自記事」という他にない資産を差別化軸にした。差別化軸: 「ただ動くツールではなく、"なぜその答えになるのか"を実装レベルで説明できるツール集」。
- 既存コード（`src/app/pages/articles-page/articles-list.ts`の`relatedTools`）に、記事と対応するツールを紐づける仕組みが既に実装として存在しており、この戦略と噛み合うことを設計判断の裏付けとした。
- URLは変更せず（/ja, /enのまま）新ランディングページに差し替える方針とした。新URLへの移行+リダイレクトは、過去のインシデント（2026-06-21のcanonical/hreflang/sitemap末尾スラッシュ方針転換によるURL正規化移行事故、詳細は`docs/core/tech/incident-report-indexing.md`）と同種の「正規化移行イベント」を再発させるリスクがあるため却下した。
- 却下した代替案:
  - 現ダッシュボードの見た目を維持しつつ静的HTML化するだけの対応 → テンプレ的な構造自体は変わらず、差別化にならないため却下
  - 記事一覧をそのまま新着順で羅列する構成 → 実装は容易だが独自価値が伝わりにくく、今回の目的（テンプレ脱却）を達成しにくいため却下

## ユーザーストーリー
- 検索エンジンからJSON整形等のキーワードで訪れた開発者として、devToolsのトップページで「このツールは実装をちゃんと検証している」と分かる情報を見て、安心してツールを使い始めたい。それによって、単なるツール一覧サイトとの違いを感じ、再訪・他ツールの利用につながる。
- 頻繁にこのサイトを使う常連ユーザーとして、よく使うツールを自分好みに並べたダッシュボード（/dashboard）を使いたい。それによって、毎回メニューから探す手間を省ける。
- サイト運営者として、新ランディングページがGoogleにインデックスされ、検索エンジン経由の流入を得たい。それによって、サイトの認知・利用者拡大につながる。

## フェーズ定義
| フェーズ | 対象機能 | 説明 |
|---|---|---|
| MVP（今回のスコープ） | ランディングページ新設＋ダッシュボード分離 | トップページの静的LP化、既存ダッシュボードの/dashboard移設・noindex化 |
| Phase 2（将来対応） | 記事の追加拡充・Topic Cluster化 | 各ツールに対応する深掘り記事を増産し、「実装を検証したツール」セクションを充実させる（本仕様のスコープ外） |

## 機能要件

### 1. ランディングページ本体（/ja, /en）
- 既存の`dashboard-page`コンポーネントに代わり、新規`landing-page`コンポーネントをルート`''`（トップ）に配置する
- 全セクションはSSG（静的サイト生成）時点で完全なHTMLとして出力されること（`@defer`や後からJSで動的注入される形にしない。Issue #220で判明した「SSG出力にコンテンツが含まれない」問題の再発防止のため必須要件とする）
- 6セクションを上から順に配置する:
  1. ヒーロー
  2. ツールカテゴリ一覧
  3. 「実装を検証したツール」（記事×ツール統合）
  4. なぜ安心して使えるか
  5. 更新履歴
  6. フッター導線

#### 1-1. ヒーローセクション
- サイトの独自コンセプトを表す見出し・本文を配置する（方向性の例: 「実装を検証した開発者ツール集」。最終コピーの文言はコンテンツ作成時に確定してよい）
- ja/enそれぞれ独立したコピーとする（en版はja版の直訳であってはならない。`docs/products/en-content-quality/policy.md`準拠）
- ダッシュボード（/dashboard）への副次的な導線（CTA）を1つ配置する

#### 1-2. ツールカテゴリ一覧セクション
- `src/resources/menu/def/menu-def.ts`の`MENU_CATEGORIES`定義に基づき、全12ツールをカテゴリ別に静的リンクとして表示する
- 各ツールに1〜2文の説明文を付与する（既存の`menu-def.ts`のdescriptionを流用してよい）
- 各ツールへのリンクは個別ツールページへの直リンクとする（/dashboard経由にしない）

#### 1-3. 「実装を検証したツール」セクション
- `src/app/pages/articles-page/articles-list.ts`の`relatedTools`を用いて、記事とそれに対応するツールをペアで表示する
- 表示形式: 記事タイトル（見出し）＋要約＋対応するツールへのリンク
- 対応する記事がないツールについては、このセクションに含めない（現状6記事分のペアのみ表示される）
- 業務ルール: 「記事とツールのペア表示は`relatedTools`データに完全に駆動される」とし、将来の記事追加に対して自動的にセクションが拡張される実装とする（ハードコードで個別ケースを列挙しない）。このルールが成り立たない例外ケース（1つの記事が複数ツールに関連する場合等）は明確には見つからなかったが、`relatedTools`が配列型であれば複数ツールへの関連付けにも自然に対応できる設計とする

#### 1-4. 「なぜ安心して使えるか」セクション
- クライアントサイド処理・データ送信なし・インストール不要の3点を簡潔に訴求する
- 動作原理を解説した記事があればリンクを添える
- このセクションを主役にせず、他セクション（特にS3）より小さく・控えめに配置する

#### 1-5. 更新履歴セクション
- 既存の`update-history-card`のデータを静的に直近5件程度表示する

#### 1-6. フッター導線セクション
- ダッシュボード（/dashboard）、サイトマップ、運営者情報、お問い合わせ（GitHub Issues）へのリンクを配置する

#### 1-7. 広告の配置
- ヒーロー直下・本文最上部には広告を配置しない（過去のcookie同意バナーの侵入型インターステイシャル問題の教訓を踏襲し、ファーストビューを圧迫しない）
- セクション間（例: S3とS4の間）またはフッター上部に1枠配置する

### 2. ダッシュボードの分離（/dashboard）
- 既存の`dashboard-page`コンポーネント（カードのドラッグ&ドロップ・リサイズ・localStorage永続化を含む）を、ルート`/dashboard`（`/ja/dashboard`, `/en/dashboard`）に移設する
- 機能・見た目は現状維持する。Issue #220で修正済みのSSG出力・`NgComponentOutlet`による宣言的レンダリングもそのまま維持する（退行させない）
- `src/resources/menu/def/menu-def.ts`の`MENU_DASHBOARD.routerLink`を`/`から`/dashboard`に変更する

### 3. ダッシュボードのnoindex化
- `/dashboard`配下のページに`<meta name="robots" content="noindex,follow">`を付与する（`follow`を残し、ツールページへのリンク評価は継続させる）
- sitemap.xml生成処理（`scripts/postbuild.mjs`）から`/dashboard`配下のURLを除外する
- robots.txtでの`Disallow`は行わない（metaタグによるnoindex認識のためクロール自体は許可する。過去のインシデントで`robots.txt`の`Disallow: /{locale}/error/`のみという既存パターンを踏襲）

### 4. i18n対応
- ランディングページの新規テキストはすべて`$localize`でカスタムIDを付与する
- `yarn ng extract-i18n`実行後、`messages.en.xlf`にen版翻訳を追加する
- en版はja版からの逐語訳であってはならない。文構成・具体例のいずれかを変える（`docs/products/en-content-quality/policy.md`準拠）

## 受け入れ条件
- [ ] `yarn build`後、`dist/ng-devtools/browser/ja/index.html`（およびen側）の生HTMLに、6セクション全てのテキストコンテンツが含まれていることをgrep等で確認できる
- [ ] ツールカテゴリ一覧セクションから全12ツールへの`<a>`タグが静的HTMLに含まれている
- [ ] 「実装を検証したツール」セクションに、現在の6記事に対応するペアが表示され、各ツールへのリンクが含まれている
- [ ] `/dashboard`（ja/en）にアクセスすると、現行のカードグリッドUI（ドラッグ&ドロップ・リサイズ・Reset・localStorage永続化）が従来通り動作する
- [ ] `/dashboard`のHTMLに`<meta name="robots" content="noindex,follow">`が含まれている
- [ ] sitemap.xmlに`/dashboard`関連URLが含まれていない
- [ ] `menu-def.ts`のダッシュボードメニュー項目のリンク先が`/dashboard`になっている
- [ ] en版のヒーロー・各セクション見出しテキストがja版の逐語訳になっていない
- [ ] `yarn test`が全てパスする
- [ ] ハイドレーション警告（NG05xx等）が発生しない

## エッジケース・異常系
| ケース | 期待する挙動 |
|---|---|
| 記事が0件の場合（将来的に記事が全て削除された等） | 「実装を検証したツール」セクション自体を非表示にする（空の見出しだけ残さない） |
| ツールに対応する記事が存在しない場合 | そのツールは「実装を検証したツール」セクションに表示されず、ツールカテゴリ一覧のみに表示される |
| localStorageが利用不可（プライベートブラウジング等）な環境で/dashboardにアクセス | 既存の`PlatformService`経由のガードにより、レイアウトはデフォルト表示にフォールバックする（現行仕様を維持し、新規対応は不要） |
| 旧URL（/）への直接アクセスでダッシュボード機能を期待するユーザー | ランディングページのヒーローセクションにダッシュボードへの導線があるため迷わない設計とする |

## 非機能要件
- **レスポンシブ対応**: PC＋スマホ（既存の他ページと同様の対応レベル）
- **アクセシビリティ**: 既存ページと同水準（見出し階層・aria属性等の既存パターンを踏襲）
- **パフォーマンス**: 新規セクションは静的HTML中心のため、既存ダッシュボードのような動的レイアウト計算は不要。Core Web Vitalsへの悪影響がないこと

## スコープ外
- 記事の追加執筆・Topic Cluster化（Phase 2で別途対応）
- ダッシュボード機能自体の変更・改善（既存のIssue #220での修正を維持するのみ）
- 他ロケール（ja/en以外）への対応
- GSCでの実際のインデックス登録状況の確認・監視（別途運用対応）

## 優先度
| 機能 | 優先度 | 理由 |
|---|---|---|
| ランディングページ本体（6セクション） | Must | 本仕様の主目的 |
| ダッシュボードの/dashboard移設 | Must | ランディングページ化の前提条件 |
| noindex化 | Must | ダッシュボードが検索結果に混在しないようにするため必須 |
| 「実装を検証したツール」セクション | Must | 差別化戦略の核 |
| i18n（en独自コピー） | Must | 過去のen版未インデックス問題の教訓 |
| 記事の追加執筆 | Won't（今回） | Phase 2 |

## リスク・依存関係
- ルーティング変更（`menu-def.ts`, `app.routes.ts`）は既存の内部リンク・サイトマップに影響するため、変更漏れがないか要確認
- 本仕様の効果（インデックス登録改善）はGoogleの評価プロセスに依存するため、実装後即座に効果が出るとは限らない。中長期的に監視する必要がある
- en版コピーライティングの品質が、過去のen版未インデックス問題を再発させるかどうかの鍵になるため、慎重な作成が必要
