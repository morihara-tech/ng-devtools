# インシデント調査報告: Google Search Console インデックス登録失敗

- 調査日: 2026-07-04
- 調査者: テックリード
- 対象: https://devtools.morihara.tech （Angular 21 SSG / S3 + CloudFront / ja・en 2ロケール）
- 事象: 6月中旬のインデックス再登録依頼後、「クロール済み - インデックス未登録」38件、「代替ページ（適切なcanonicalタグあり）」12件、インデックス成功はわずか4件

---

## 1. 結論（サマリ）

**主因は AdSense スクリプトではなく、6/21 の canonical/hreflang/sitemap の末尾スラッシュ方針転換（PR #171 / commit 813fb4b）によって、サイト全体の「URL正規化の引っ越し（canonical migration）」が発生したこと。**
Google は全52ページ×スラッシュ有無2バリアント＝約100 URLの正規URL選定をやり直しており、現在の GSC ステータスの大半はその**移行途中の状態**である。ただし、以下の**実在する技術的欠陥**が移行を遅延・妨害しており、放置すると悪化が固定化するリスクがある。

| # | 欠陥 | 深刻度 |
|---|---|---|
| 1 | ロケールトップの canonical（`/ja`, `/en`）が **301リダイレクトするURL** を指している | 高 |
| 2 | 全ページの hreflang x-default が `/ja`（301リダイレクトURL）を指している | 高 |
| 3 | sitemap.xml の先頭エントリ `/ja`・`/en` が301リダイレクトURL | 中 |
| 4 | 下層ページはスラッシュ有無どちらも200を返し、301による統合がない（canonical頼み） | 中 |
| 5 | sitemap.xml の `<lastmod>` が全URL一律「ビルド日」になり、デプロイのたびに全ページ更新扱いになる | 中 |
| 6 | ページの title/description が薄い（トップは `devTools` のみ、description は1文） | 中（品質評価に影響） |

AdSense スクリプト注入は **5/16 導入・`async` 属性付き・`</head>`直前に1回のみ・重複ガードあり**で、レンダリングブロックせず、導入後もインデックスされていた実績があるため、**原因である可能性は低い**。

## 3. 原因分析

### 3.1 なぜ ja のオリジナルページまで「クロール済み - インデックス未登録」なのか

「en訳の品質不足」仮説では ja ページの脱落を説明できないが、**canonical移行仮説なら全ページを説明できる**。

- 6/21以前: canonical・sitemapは「スラッシュあり」→ Googleは `/ja/json-formatter/` 形式を正規URLとしてインデックスしていた
- 6/21以降: canonical・sitemapが「スラッシュなし」に一斉反転 → Googleにとっては**全URLの正規変更（サイト移転に近いイベント）**
- Googleは旧正規URL（スラッシュあり）をインデックスから落とし、新正規URL（スラッシュなし）を再評価キューに積む。この間、新旧両バリアントが「クロール済み - インデックス未登録」に滞留する
- 38件リストにスラッシュあり/なしの**両方**が混在していること、インデックス成功4件に旧形式（`/en/url-encoder/`, `/ja/api-key-generator/`）と新形式（`/ja/url-encoder`）が混在していることは、まさに移行途中である証拠

### 3.2 「代替ページ（適切なcanonicalタグあり）」12件の解釈

**実害なし（正常動作＋旧状態の残骸）と判断する。**

- このステータスは「重複URLだが、正しいcanonicalで正規ページに統合済み」という**Googleの正常な重複処理**
- 12件の大半がスラッシュ「なし」URLである点は一見矛盾するが、これは**6/21以前のクロール結果の残骸**（当時スラッシュなしURLのHTMLにはスラッシュありへのcanonicalが書かれていた）で、再クロールされ次第ステータスが更新される。「以前より少し減少」しているのはその進行の表れ
- 対応不要。むしろ件数減少は移行が進んでいるシグナル

### 3.3 移行を遅延させている実在の欠陥（要修正）

1. **ロケールトップの矛盾シグナル（最重要）**: canonicalは `/ja`（スラッシュなし）と宣言しているのに、サーバー（CloudFront Function）は `/ja` を `/ja/` へ301する。「canonicalが指す先がリダイレクト」はGoogleが最も嫌う矛盾で、正規URL選定を混乱させる。`/en/` が未登録のまま・`/ja/` はGoogleがcanonical宣言を**無視して**スラッシュありでインデックスした、という現状はこの矛盾の直接的な帰結
2. **hreflang破壊**: x-default（全ページ）とトップページのhreflang相互リンクが301 URLを指すため、hreflangクラスタとして無効化されている可能性が高い。ja/en間の言語別評価が効かず、en側が「jaの重複」と誤判定されるリスクを高める
3. **重複配信の常態化**: 下層ページはスラッシュ有無で同一コンテンツを200配信しており、統合はcanonical頼み。クロールバジェットを2倍消費し、正規選定を遅くする
4. **lastmod の信頼性低下**: デプロイごとに全URLの `<lastmod>` が更新され、6月中旬の連日デプロイで「全ページが毎日更新された」ように見えた。Googleはlastmodが信頼できないsitemapのシグナルを軽視するようになる
5. **（既知の継続課題）コンテンツ品質**: ドメインが若く権威性が低い中、ツールページの固有テキストは約1,000字・descriptionは1文。「クロール済み - インデックス未登録」はGoogleの品質しきい値未達ページの典型ステータスでもあり、移行が落ち着いた後もこの層は残り得る。#160のen独自コンテンツ化は正しい方向であり継続すべき

### 3.4 棄却した仮説

- **AdSenseスクリプトのレンダリングブロック/CLS**: `async` 属性付きで注入は1回のみ。導入は5/16で、その後もインデックスされていた実績があるため主因ではない。広告ユニット未配置のため CLS への影響も限定的
- **robots.txt / sitemap.xml の誤変更**: 6月の変更でこれらは壊れていない（実測で正常応答・整合を確認）
- **prerender出力の破損**: 静的HTMLに本文・ヘルプが含まれることを実測で確認。破損なし

### 3.5 「以前成功していたページの削除」は悪化か一時的か

**構造的には「canonical移行に伴う一時的な入れ替え期」**だが、3.3の矛盾シグナルを放置すると「一時的」が長期化・固定化する。移行イベント自体は6/21起点でまだ約2週間であり、シグナルを整合させれば2〜6週間で回復が見込めるのが一般的な経験則。ただし低権威ドメインでは再イン デックスの優先度が低く、修正なしでは回復が保証されない。

## 4. 推奨対応（優先順位順）

### P1: シグナルの完全整合（実装はフロントエンド/EMへ依頼）

方針: **「末尾スラッシュなし」を正とする現行方針を維持**し（再度の方針転換は移行イベントの二重発生になるため厳禁）、矛盾している箇所だけを直す。

1. **CloudFront Function を修正**: `/ja` `/en` の「スラッシュなし→あり301」をやめ、逆に**全パスで「スラッシュあり→なし301」**に統一する（`/` → `/ja` への301は維持）。これで canonical・sitemap・内部リンク・サーバー応答の4シグナルが完全一致し、重複配信も解消される
   - 代替案（CloudFront側を触りたくない場合）: ロケールトップのみ canonical/hreflang/sitemap を `/ja/` `/en/` （スラッシュあり）に特別扱いする postbuild 修正。ただしサイト内でルールが2つになるため次善策
2. **x-default の修正**: 上記1を採る場合は現状 `/ja` のままで整合する。代替案の場合は `/ja/` へ変更

### P2: sitemap.xml の lastmod 改善

- 全URL一律ビルド日をやめる。ルートごとに関連ソースの git 最終コミット日を使うか、少なくとも安易に毎デプロイで更新しない

### P3: 回復オペレーション（コード外・COO/ユーザー側の作業）

- P1デプロイ後、Search Console で sitemap.xml を再送信
- 主要ページ（ja/enトップ、json-formatter、url-encoder 等 上位10ページ程度）を URL検査→インデックス登録リクエスト
- **以後2〜4週間は正規化・URL構造に関わる変更を凍結**し、GSCの週次観測に徹する（毎週の件数推移を記録）

### P4: 品質改善の継続（中期）

- #160 の en 独自コンテンツ化を完遂
- 各ページの `<title>`（トップが `devTools` のみは弱い）と meta description（1文→検索意図を含む80〜120字）を固有化
- 構造化データ（SoftwareApplication / FAQPage 等）の付与を検討

### 再発防止

- 「canonical・sitemap・内部リンク・サーバー応答（リダイレクト）の4点は常に同一のURL形式を指す」ことをリリースチェックリスト化
- postbuild に検証ステップを追加: 生成した canonical/sitemap の全URLに対して本番（またはステージング）で200が返ることをCIで確認する
